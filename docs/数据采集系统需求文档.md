## 1. 背景与目标

学校需要持续汇聚专业、师资、教学、科研和学生数据。当前需求包含两类数据来源：校内人员填报、业务系统 API 采集；采集结果还需要反向为各业务系统提供统一数据服务。

建设目标：

1. 统一十二类核心数据的字段口径、采集入口和审核流程。
2. 支持传统表单填报，以及“文件 + 提示词 + 大模型”辅助填报。
3. 支持业务系统 API 定时或手动拉取，保留来源和处理记录。
4. 通过校验、去重、审核和版本管理提高数据可信度。
5. 仅将已发布数据通过统一 API 提供给授权业务系统。
6. 对个人信息、科研成果和文件的全生命周期进行权限控制和审计。

### 1.1 建设原则

- **一数一源**：每个字段明确权威来源和归属部门，避免多头维护。
- **先确认再发布**：AI 提取、API 采集和人工填报均须经过适用的人工确认或审核。
- **原始数据可追溯**：保留来源系统、原始文件、原始报文、修改历史和审核记录。
- **配置优先**：字段、字典、校验规则、接口映射尽量配置化，减少重复开发。
- **敏感信息最小化**：采集和共享遵循必要、授权、可审计原则。

### 1.2 非建设目标（首版）

- 不替代人事、教务、科研、学工等业务系统的原始业务流程。
- 不建设通用 BI 大屏、复杂数据仓库或完整主数据管理平台。
- 不承诺大模型无人工复核即可形成正式数据。
- 首期不包含扫描件 OCR；扫描版 PDF 和无文本图片需后续单独评估。
- 不在未明确下游协议前实现双向实时同步；首版以标准化只读共享 API 为主。

## 2. 用户与职责

| 角色 | 主要职责 | 数据范围 |
| --- | --- | --- |
| 教师 | 填写和维护本人的教师类数据，上传材料，确认 AI 提取结果，修改退回数据 | 本人数据 |
| 系部数据管理员 | 代本系部教师填写教师类数据；对本系部教师提交的数据进行系部初审 | 本系部 |
| 业务部门审核员 | 组织人事部、科研处、教务处的审核员，对所负责数据域既能审核也能填写；教务处审核员负责填写专业、课程、授课和在校生数据 | 所负责数据域，全校 |
| 信息中心管理员 | 可填写全部数据；终审并发布；可跳过系部初审和业务部门审核直接发布；负责用户权限、字典、数据标准、接口和系统运行管理 | 全校全部数据 |
| 数据使用方/业务系统 | 查询已发布数据，接收变更信息 | 按应用授权的数据域和字段 |
| 审计人员 | 查看操作、审核和共享日志 | 只读审计范围 |

审批流程见 3.3 节，各数据域的填写与审核权限见 3.4 节。教师不能审核本人提交的数据。

## 3. 建设范围

### 3.1 十二类数据及责任部门

| 编号 | 数据域 | 标准表 | 填写方 | 业务审核部门 | 业务主键/唯一性依据 |
| --- | --- | --- | --- | --- | --- |
| D01 | 专业设置数据 | `ODS_ZYSZSJ` | 教务处 | 教务处 | 专业代码 |
| D02 | 教职工基本信息 | `ODS_JZGJBSJ` | 教师 / 系部 | 组织人事部 | 教工号 |
| D03 | 教师培训与交流 | `ODS_XXJXSJ` | 教师 / 系部 | 组织人事部 | 工号 + 项目名称 + 类型 + 地点 |
| D04 | 教师获奖信息 | `ODS_JSHJSJ` | 教师 / 系部 | 所属教学系（系部） | 第一获奖人工号 + 获奖名称 + 获奖日期 |
| D05 | 教师论文著作 | `ODS_LWZZSJ` | 教师 / 系部 | 科研处 | DOI/ISBN；无编号时使用题名 + 类型 + 年份 |
| D06 | 纵向科研项目 | `ODS_KYXMJBSJ` | 教师 / 系部 | 科研处 | 项目编号 |
| D07 | 横向课题 | `ODS_HXKTSJ` | 教师 / 系部 | 科研处 | 校内课题编号或合同编号 |
| D08 | 教师企业实践锻炼 | `ODS_JSQYJZSJSJ` | 教师 / 系部 | 组织人事部 | 工号 + 企业 + 开始日期 |
| D09 | 教师知识产权 | `ODS_ZSCQSJ` | 教师 / 系部 | 科研处 | 专利号/登记号/授权号 |
| D10 | 课程基本数据 | `ODS_KCJBSJ` | 教务处 | 教务处 | 课程代码 |
| D11 | 授课信息 | `ODS_SKXXSJ` | 教务处 | 教务处 | 学期 + 课程代码 + 教学班号 |
| D12 | 全日制高职在校生基本信息 | `ODS_XSJBSJ` | 教务处 | 教务处 | 学号 |

表中“教务处”“组织人事部”“科研处”指该部门的业务部门审核员，他们对所负责数据域既能填写也能审核。信息中心对以上全部数据域均有填写权限。

教师获奖信息由所属教学系审核，没有单独的职能部门审核环节（见 3.3.2 节）。九月新生数据（`ODS_XSXSSJ`）不纳入首版，后续单独处理。

### 3.2 数据生命周期

```text
人工表单 ─────────────────────────────┐
电子表格导入 → 程序解析 → 逐行校验 ──────┤
文件上传 → 异步解析 → AI 提取 → 人工确认 ─┤
业务系统 API → 原始报文 → 映射/清洗 ─────┤（最后对接）
                                       ↓
                                草稿（填报记录表）
                                       ↓
                                  校验/查重/提交
                                       ↓
                       系部初审 → 业务部门审核 → 信息中心审核
                       （任一环节可退回；信息中心可跳过前两级）
                                       ↓
                           发布：写入 ODS_* 标准表并生成版本
                                       ↓
                                下游查询/变更通知
```

草稿和审核中的数据只保存在填报记录表中；`ODS_*` 标准表只保存已发布的当前版本。AI 候选在确认前保存在候选表中，确认后才成为草稿。

### 3.3 审批流程

#### 3.3.1 记录状态

| 状态 | 含义 |
| --- | --- |
| `draft` 草稿 | 已保存未提交，填写人可修改、删除 |
| `pending_dept` 待系部初审 | 教师提交后，等待所属系部初审 |
| `pending_domain` 待业务部门审核 | 等待该数据域的业务审核部门审核 |
| `pending_center` 待信息中心审核 | 等待信息中心终审 |
| `returned` 已退回 | 任一审核环节退回，填写人修改后可重新提交 |
| `published` 已发布 | 已写入 `ODS_*` 标准表，可对外共享 |
| `archived` 已归档 | 不再使用的已发布记录，保留历史版本 |

#### 3.3.2 标准流程

```text
教师填写 → 提交 → 系部初审 → 业务部门审核 → 信息中心审核 → 发布
                    ↓            ↓              ↓
                   退回         退回           退回  → 填写人修改后重新提交
```

提交后的第一个审核环节由填写方决定：

| 填写方 | 提交后进入 | 说明 |
| --- | --- | --- |
| 教师 | 待系部初审 | 完整三级审核 |
| 系部数据管理员（代填本系部教师数据） | 待业务部门审核 | 系部本身即填写方，视为系部初审已通过 |
| 业务部门审核员（填写本部门负责的数据域，如教务处填写专业、课程、授课、在校生） | 待信息中心审核 | 填写方即业务审核部门，提交即视为业务审核通过；这类数据没有系部初审 |
| 信息中心 | 可直接发布，或提交进入待信息中心审核 | 信息中心对全部数据有填写和发布权限 |

教师获奖信息（D04）的业务审核由所属教学系完成，系部初审即业务审核，流程为：

| 填写方 | 流程 |
| --- | --- |
| 教师 | 待系部初审 → 待信息中心审核 → 发布 |
| 系部数据管理员 | 待信息中心审核 → 发布 |
| 信息中心 | 可直接发布 |

#### 3.3.3 审核规则

1. 每一级审核人只能“通过”或“退回”；退回必须填写意见，记录回到填写人，状态为“已退回”。
2. 退回后重新提交，从该记录填写方对应的第一个审核环节重新开始，不保留之前各级的通过结果。
3. 信息中心可在任一待审环节直接发布，跳过尚未完成的系部初审和业务部门审核；跳级发布必须填写说明，流转记录标记为“跳级发布”并写入审计日志。
4. 信息中心也可在任一待审环节退回。
5. 审核人不能审核本人填写的记录；信息中心的跳级发布除外，但须留痕。
6. 提交后、第一个审核动作发生前，填写人可撤回为草稿。
7. 已发布记录需要修改时，基于当前版本生成新的草稿并重新走流程；新版本发布前，`ODS_*` 和共享接口仍提供原版本。
8. 每次通过、退回、撤回、跳级发布、归档都记录操作人、时间、意见、前后状态和字段差异。

#### 3.3.4 各级审核人

| 审核环节 | 审核人 | 审核范围 |
| --- | --- | --- |
| 系部初审 | 记录所属系部的系部数据管理员 | 本系部教师提交的教师类数据 |
| 业务部门审核 | 该数据域业务审核部门的审核员（见 3.1 节）；获奖信息无此环节 | 所负责数据域的全校数据 |
| 信息中心审核 | 信息中心管理员 | 全部数据域 |

### 3.4 数据填报权限

| 数据域 | 教师 | 系部数据管理员 | 业务部门审核员 | 信息中心 |
| --- | --- | --- | --- | --- |
| 教职工基本信息、培训、企业实践（D02、D03、D08） | 填写、查看本人数据 | 填写、查看、初审本系部教师数据 | 组织人事部：全校填写、查看、审核 | 全部数据填写、查看、终审、发布 |
| 论文著作、纵向项目、横向课题、知识产权（D05–D07、D09） | 填写、查看本人数据 | 填写、查看、初审本系部教师数据 | 科研处：全校填写、查看、审核 | 同上 |
| 教师获奖信息（D04） | 填写、查看本人数据 | 填写、查看、审核本系部教师数据 | — | 同上 |
| 专业、课程、授课、在校生（D01、D10–D12） | — | — | 教务处：全校填写、查看、审核 | 同上 |

补充规则：

- 教师类数据通过记录中的教工号（如 `JGH`、第一获奖人工号、项目负责人工号）判定“本人”，教工号与登录账号一致；通过所属院系部判定“本系部”。
- 教师和系部数据管理员必须在用户管理中设置所属系部，否则不能填写教师类数据。
- 教师不能查看同系部其他教师的数据。
- 业务部门审核员只能填写、查看和审核本部门负责的数据域，按所在部门判定（组织人事部 `BM11`、科研处 `BM22`、教务处 `BM07`）。
- 业务部门审核员不能审核本人填写的记录；本人填写的记录提交后直接进入信息中心审核。
- 身份证号明文保存；列表和详情默认脱敏显示，查看明文和导出需单独权限并记录审计。

## 4. 功能需求

### 4.1 账号、组织与权限

- F-001：支持用户登录、退出、找回/重置密码和会话失效；管理员可创建、停用用户。
- F-002：维护学校、系部、专业、班级等组织关系，一个用户可关联一个或多个数据范围。
- F-003：采用 RBAC（角色权限）与数据范围控制，权限至少细化到数据域、操作和字段。
- F-004：支持教师本人范围、系部范围、职能部门数据域范围和全局管理范围。
- F-005：身份证号明文保存；身份证号、手机号等敏感字段默认脱敏显示，导出和查看明文需独立权限并记录日志。
- F-006：下游系统使用独立应用凭证，不使用个人账号；凭证支持过期、轮换和撤销。

### 4.2 数据目录与标准

- F-010：展示十二类数据目录、填报说明、责任部门、字段定义和更新时间。
- F-011：字段配置包括名称、编码、类型、是否必填、长度、字典、默认值、脱敏级别和校验规则。
- F-012：维护统一字典，如性别、职称、学历、学位、项目级别、学期、知识产权类型。
- F-013：数据结构和字典变更须带版本；历史记录仍可按原版本解释。
- F-014：支持生成与当前字段版本一致的填报模板和字段说明。

### 4.3 表单填报

- F-020：按权限提供单条新增、查看、编辑、复制新增、删除草稿和提交审核。
- F-021：列表支持分页、组合筛选、排序、列显隐和权限范围内的数据导出。
- F-022：表单执行前后端双重校验，包括必填、格式、字典、日期区间、金额和关联数据有效性。
- F-023：支持草稿保存；自动保存可作为增强项，不得因自动保存而自动提交。
- F-024：提交前执行重复数据提示；疑似重复由用户选择继续、合并或取消，明确重复则阻止提交。
- F-025：退回时须填写意见，用户可查看意见并基于原记录修改重报。
- F-026：附件与业务记录关联，支持权限内查看和下载；删除正式记录采用归档或软删除。
- F-027：电子表格导入。按数据域下载与当前字段版本一致的模板，上传 `.xlsx` / `.csv` 后由程序解析（不经过大模型），逐行校验并给出错误报告；用户选择有效行生成草稿或直接提交，导入记录同样执行 3.3 节审批流程。在业务系统接口对接前，教务处数据以此方式批量采集。

### 4.4 文件与大模型辅助填报

- F-030：用户选择目标数据表，上传文件，可输入提示词补充提取范围、年份、人员或字段要求。
- F-031：首版支持 `.xlsx`、`.xls`、`.csv`、`.pdf`、`.docx`；按文件扩展名、MIME 类型和实际内容共同校验。
- F-032：上传接口仅完成安全检查和任务登记，立即返回任务 ID；解析、抽取和模型调用通过 arq + Redis 异步执行。
- F-033：任务状态包括排队、解析文件、模型提取、待确认、完成、失败、取消；展示进度、失败原因和可重试操作。
- F-034：表格文件优先用程序解析，PDF 提取文本/表格，Word 提取段落/表格；不将所有文件直接交给模型。
- F-035：模型按目标表的版本化 JSON Schema 输出结构化候选记录；后端使用 Pydantic 校验，非法输出不得入库为正式记录。
- F-036：确认页面展示原始值、标准字段值、来源位置、置信/风险提示和校验错误，支持编辑、删除、全选或逐条采纳。
- F-037：用户确认后才生成草稿；提交审核与正式发布仍执行统一流程，AI 不得绕过审核。
- F-038：保存模型提供方、模型版本、提示词模板版本、任务耗时和结果摘要；密钥及完整敏感报文不得写入普通日志。
- F-039：模型调用支持超时、限流和有限重试；模型不可用时允许下载已解析内容或改用手工填报。
- F-040：DeepSeek 仅作为首阶段验证提供方，通过可切换的 OpenAI 兼容配置接入；后续可替换为校内模型，不改变业务接口。
- F-041：上传文件设置大小、页数、行数和任务时长上限；超限须明确提示，避免任务长期占用资源。
- F-042：原始文件、提取中间结果按保留策略清理；用户可删除未进入审核流程的上传材料。

### 4.5 业务系统 API 采集

本节能力在其他功能完成后最后对接；在此之前，相关数据通过电子表格导入（F-027）采集。

- F-050：配置来源系统、数据域、接口地址、认证方式、增量参数、分页方式、字段映射和调度规则。
- F-051：支持手动立即采集和定时采集；同一来源同一数据域避免并发重复执行。
- F-052：支持全量初始化和按更新时间/游标增量采集；记录水位线，失败重试不得跳过未处理数据。
- F-053：保存原始报文或其受控归档引用、来源主键、采集批次、字段映射版本和转换错误。
- F-054：按来源系统 + 来源主键幂等写入；重复拉取不得生成重复记录。
- F-055：对来源更新采用可配置冲突策略：可信源覆盖非关键字段、生成待审核变更或仅告警；不得静默覆盖人工审核值。
- F-056：无效记录进入隔离区，支持查看原因、修复映射后重放；单条失败不掩盖批次其他结果。
- F-057：接口地址采用白名单并限制内网访问策略，防止任意 URL 请求；凭证加密保存且不回显。
- F-058：提供批次统计：总数、新增、更新、跳过、失败、耗时；支持失败重试和审计查询。

### 4.6 审核、发布与版本

- F-060：按 3.3 节执行系部初审、业务部门审核、信息中心审核三级流程，并支持信息中心跳级发布；审核人可查看字段详情、附件、来源和修改差异。
- F-061：审核通过、退回、撤回和归档均记录操作人、时间、意见和前后状态。
- F-062：发布后生成不可变数据版本；修改正式数据产生新版本，不直接覆盖历史版本。
- F-063：同一记录的新版本发布按明确策略替代当前版本，历史版本仍可追溯。
- F-064：提供待办列表，支持按系部、数据域、状态和提交时间筛选。

### 4.7 数据共享服务

- F-070：提供统一 REST API，支持按数据域分页查询、条件过滤、单条查询和按更新时间增量查询。
- F-071：下游默认只能读取 `published` 当前版本；草稿、待审核和退回数据不得共享。
- F-072：响应包含数据版本、字段结构版本、记录更新时间和分页信息，便于下游核对。
- F-073：应用授权控制数据域、字段和行范围；学生与教职工敏感字段按需单独授权。
- F-074：支持限流、超时、请求 ID、调用日志和错误格式统一；不在日志中记录完整敏感响应。
- F-075：Webhook 或消息通知作为第二阶段能力，首版可通过增量 API 完成下游同步。
- F-076：提供 OpenAPI 文档、示例和测试环境；破坏性接口变更通过版本号管理。

### 4.8 运行管理与审计

- F-080：展示填报进度、待审核数量、采集任务和失败任务，不以未经确认的数据形成正式统计。
- F-081：管理员可查看和重试失败任务，但不得代替业务审核人修改审核结论。
- F-082：记录登录、填报、导入、确认、审核、发布、导出、授权和下游调用日志。
- F-083：审计日志防普通业务用户篡改，支持按人、记录、时间和操作检索。

## 5. 数据需求

### 5.1 通用字段

各业务表除专有字段外，建议包含：

- 内部 UUID、业务主键、数据域、结构版本。

### 5.3 数据质量规则

- 完整性：关键身份、归属、时间和状态字段必填。
- 唯一性：按数据域唯一规则查重，跨来源同时保留内部 ID 和来源 ID。
- 一致性：教师工号、专业代码、课程代码等必须关联有效主数据。
- 合法性：字典值、日期、金额、人数、学时和证件格式符合规则。
- 时序性：结束日期不早于开始日期；项目状态与关键日期相互一致。
- 准确性：AI 候选值必须人工确认；API 转换异常进入隔离区。
- 及时性：按数据域设定填报周期和采集频率，逾期提醒属于增强功能。

## 6. 外部接口建议

管理接口前缀为 `/api`，对外共享接口前缀为 `/open/v1`。字段在详细设计阶段冻结。

| 模块 | 方法与路径示例 | 说明 |
| --- | --- | --- |
| 健康检查 | `GET /health` | 服务存活检查 |
| 认证 | `POST /api/auth/login` | 自建 JWT（PyJWT）+ argon2，登录账号为教工号 |
| 数据目录 | `GET /datasets` | 获取可见数据域和字段版本 |
| 业务数据 | `GET/POST /datasets/{code}/records` | 查询或新建草稿 |
| 单条记录 | `GET/PATCH /records/{id}` | 查看或编辑 |
| 工作流 | `POST /records/{id}/submit` | 提交审核 |
| 工作流 | `POST /records/{id}/review` | 通过或退回 |
| 文件任务 | `POST /ingestion/files` | 上传文件并创建异步任务，返回 202 |
| 文件任务 | `GET /ingestion/tasks/{id}` | 查询进度和结果 |
| AI 候选 | `GET/PATCH /ingestion/tasks/{id}/candidates` | 查看、编辑候选记录 |
| AI 确认 | `POST /ingestion/tasks/{id}/confirm` | 将选中候选转为草稿 |
| API 来源 | `POST /sources/{id}/runs` | 手动触发采集 |
| 共享数据 | `GET /open/datasets/{code}/records` | 应用凭证访问已发布数据 |
| 共享增量 | `GET /open/datasets/{code}/changes` | 按游标/更新时间查询变更 |

统一错误响应包含 `detail` 和 `request_id`，响应头带 `X-Request-ID`。上传、采集等异步创建接口返回 `202 Accepted`。

## 7. 非功能需求

以下为初始验收建议，需结合部署资源确认：

- 性能：常规查询在约定数据量和负载下 P95 不高于 500ms；上传登记 P95 不高于 2s；大模型和文件解析不计入同步接口时延。
- 容量：首版按 100 并发在线用户、百万级业务记录设计；文件上限默认 20MB、单任务最多 10 万单元格或 500 页，可配置。
- 可用性：核心服务支持健康检查、优雅退出、失败重试；Redis 或模型服务故障不能损坏已保存数据。
- 安全：传输加密、密码安全散列、应用凭证加密、文件类型检查、限流、CORS 白名单、SQL 注入和 XSS 防护。
- 隐私：按最小权限展示；生产日志不记录密码、密钥、完整证件号、文件正文或模型完整敏感输入输出。
- 可维护性：数据库变更全部由 Alembic 管理；配置通过环境变量注入；模型提供方和存储实现可替换。
- 可审计性：关键业务操作带操作者、时间、对象和请求 ID；异步任务可追踪到批次和来源。
- 兼容性：支持学校确定的主流桌面浏览器最新两个大版本，关键填报流程适配移动端。
- 备份：数据库和原始文件分别制定备份、恢复和保留策略，并定期进行恢复演练。

## 8. 技术方案约束

- 前端：Next.js App Router、TypeScript、Tailwind CSS、shadcn/ui、Zustand、react-hook-form + zod、TanStack Table。
- 后端：FastAPI、Pydantic v2、SQLAlchemy 2.0、Alembic、PyJWT、pwdlib（argon2）。认证为自建实现。
- 文件处理：pandas、openpyxl、pdfplumber、python-docx。
- AI：先接 DeepSeek，后接自部署 OpenAI 兼容模型；业务层不依赖特定厂商 SDK。
- 异步任务：arq + Redis；耗时文件解析、模型调用、API 采集均异步执行。
- 数据库：PostgreSQL；文件首版使用受控本地/共享存储，接口保留对象存储扩展能力。
- 前端依赖安装使用 `https://registry.npmmirror.com`。

## 9. 首版验收场景

1. 教师新建培训记录，保存草稿并提交；系部初审退回后修改重报；系部初审、业务部门审核、信息中心审核依次通过后发布，记录写入 `ODS_*` 表。
2. 系部数据管理员上传含多条获奖信息的 Excel，填写提取提示词，异步查看候选值，修正错误后仅确认所选记录。
3. 上传无文本扫描 PDF 时，系统明确提示首版不支持 OCR，不产生虚假字段。
4. 模型返回缺字段或错误类型时，候选记录显示校验问题且不能直接提交。
5. 教务处按模板导入课程电子表格，错误行给出原因，有效行进入信息中心审核；再次导入同一批数据不产生重复记录。
6. 下游应用只能查询被授权且已发布的数据，越权访问返回 403，未发布记录不可见。
7. 教师无法查看同系部其他教师的数据；敏感导出产生审计日志。
8. Redis/模型短暂失败时任务显示可诊断错误，重试后不生成重复文件任务或业务记录。
9. 信息中心对一条待系部初审的记录跳级发布，须填写说明，流转记录和审计日志均有“跳级发布”记录。
10. （业务系统接口对接后）管理员配置教务课程 API，完成全量采集后再次执行，记录不重复；修改映射后可重放失败记录。

## 10. 确认事项

### 10.1 已确认（2026-11-04）

1. 草稿和审核中的数据保存在填报记录表，`ODS_*` 表只保存已发布数据。
2. 审批流程为系部初审 → 业务部门审核 → 信息中心审核发布，信息中心可跳级发布（见 3.3 节）。
3. 教师类数据由教师或所在系部填写；专业、课程、授课、在校生数据由教务处填写；信息中心对全部数据有填写权限（见 3.4 节）。
4. 身份证号明文保存。
5. 九月新生数据后续再处理，不纳入首版。
6. 业务系统接口最后对接，此前以电子表格导入采集。
7. DeepSeek 处理校内数据已获审批。
8. 公共基础教学部部门编码统一为 `BM09`。
9. 教师获奖信息由所属教学系审核，无职能部门审核环节。
10. 组织人事部、科研处、教务处各设业务部门审核员，审核员既能审核也能填写本部门负责的数据域。
11. 发送给 DeepSeek 的内容不需要剔除身份证号等敏感字段。

### 10.2 待确认

1. 业务部门审核员的正式人员名单（目前为测试账号）。
2. 学生、专业、课程等历史数据的初始化方式和电子表格样例。
3. 业务系统 API 清单、认证方式、调用限制、网络区域、增量能力和测试环境。
4. 下游系统需要的数据域、字段、同步时效、增量协议及是否必须 Webhook。
5. 是否接入学校统一身份认证；首版自建本地账号是否只作为过渡。
6. 自部署模型的 OpenAI 兼容性、并发、上下文长度、结构化输出和数据保留能力。
7. 文件保存期限、存储位置、备份要求、等保/密码合规及个人信息保护要求。
8. 预计记录量、并发量、可用性目标和部署资源，用于最终确定非功能指标。
