## 2. 架构检查结论

对照需求文档逐项检查后，现有底座方向正确，但有以下问题需要在继续扩展前处理。前两项决定后续十二张表的写法，优先级最高。

| 编号 | 问题 | 影响 | 处理方式 |
| --- | --- | --- | --- |
| A1 | 填报直接写入 `ODS_*` 表，没有状态、审核、版本、来源字段 | 违反“先确认再发布”和“原始数据可追溯”；共享接口无法区分已发布与草稿；AI 和 API 采集结果没有落点 | 新增“填报记录层”，`ODS_*` 只保存已发布数据（见第 3 节） |
| A2 | 教职工校验逻辑手写在 `staff_rules.py`（约 300 行），表单字段在前端单独写死 | 复制到 12 张表会产生大量重复代码，前后端字段口径容易不一致 | 建立数据集注册表：字段元数据统一定义，后端校验与前端表单都由它驱动，特殊规则用钩子函数补充 |
| A3 | 审核员角色为全校范围，没有按数据域授权，也没有多级审核 | 无法实现三级审批和“组织人事部审教职工、科研处审项目”；审核员现在也能填写，越权面更大 | 数据集注册表声明业务审核部门；审核员按所在部门匹配数据域；禁止审核本人填写的记录。教职工接口已先按部门临时限定 |
| A4 | 身份证号明文存储 | 已确认明文保存，不再改为加密 | 保留列表脱敏；增加明文查看与导出的单独权限和审计 |
| A5 | 前端 `lib/tables.ts` 仍是原型字段（`T_*` 表名、非标准字段） | 页面字段与标准不一致，数据表与字段页面展示错误信息 | 改为读取后端数据集元数据，删除原型字段定义 |
| A6 | 依赖与文档不一致：`fastapi-users` 已安装但未使用；需求写 `/api/v1`，实际为 `/api`；错误响应为 `detail` 而非 `code/message` | 后续开发者被误导 | 移除 `fastapi-users`；管理接口保留 `/api`，对外共享接口使用 `/open/v1`；需求文档同步修订 |
| A7 | 没有任何自动化测试 | 权限、校验和状态流转改动无法回归 | 引入 pytest + 测试库，先覆盖权限、教职工校验和状态机 |
| A8 | 业务表用部门名称 `YXBMCMC` 关联部门 | 部门改名后范围判断失效 | 记录层同时保存部门 ID 用于权限判断，`YXBMCMC` 仅作为标准字段输出 |
| A9 | 依赖已安装但未使用：TanStack Table、react-hook-form、zod、Zustand | 无直接风险 | 在通用列表和动态表单中使用前三者；Zustand 无实际需要时移除 |
| A10 | 前端只有教师、部门管理员、信息中心三种角色，菜单和页面访问按角色写死；审核员登录后被当作“部门管理员”，看到“本部门范围”和全部填报菜单 | 审核员看到不属于自己数据域的菜单，工作台和范围提示错误 | 后端 `/api/auth/me` 返回当前用户可填写、可审核的数据集；前端菜单与入口改为按这份清单生成，增加“业务部门工作台” |
| A11 | 初始化脚本会按定义覆盖角色权限、用户系部和字典项 | 在开发库重跑会冲掉界面上的修改（本次已将罗胜、谭元霸的系部同步进种子定义） | 拆分为“基础数据”和“测试账号”两部分；对已存在的记录只补缺，不覆盖界面可编辑的字段 |
| A12 | 获奖信息只有系部一级业务审核，与其他数据域的三级结构不同 | 状态机若写死三级会出现空环节 | 注册表的业务审核部门允许取“所属系部”；状态机根据填写方与数据域计算审核环节序列，跳过不存在或已由填写方完成的环节 |

## 3. 目标架构

### 3.1 分层

```text
浏览器（Next.js App Router）
  ├─ 通用数据集列表（TanStack Table，服务端分页）
  ├─ 动态表单（读取字段元数据渲染，提交前做基本校验）
  └─ 我的填报 / 审核中心 / 文件解析 / 任务与接口管理
             ↓ HTTPS / JSON
FastAPI
  ├─ 管理接口 /api/...         个人账号 JWT，RBAC + 数据范围
  ├─ 共享接口 /open/v1/...     应用凭证，只读已发布数据
  │
  ├─ 数据集注册表   字段、字典、业务主键、范围字段、校验钩子、责任部门
  ├─ 填报记录层     biz_record / biz_record_event / biz_record_version
  │                 人工、电子表格、AI、API 四种来源都先进入这里
  ├─ 发布层         ODS_* 标准表，只保存当前已发布版本
  │
  ├─ SQLAlchemy 2.0 → PostgreSQL（业务状态唯一权威来源）
  └─ arq → Redis → worker：文件解析、模型提取、来源 API 采集
```

### 3.2 填报记录层表设计

| 表 | 作用 | 主要字段 |
| --- | --- | --- |
| `biz_record` | 每条业务数据的当前工作副本 | `id`、`dataset_code`、`business_key`、`department_id`、`owner_account`、`filler_type`（teacher / department / domain / center）、`status`、`payload`（JSONB，键为标准字段编码）、`warnings`、`source_type`（manual / excel / ai / api）、`source_system`、`source_ref`、`batch_id`、`schema_version`、`published_version`、`ods_id`、创建/更新人与时间、`deleted_at` |
| `biz_record_event` | 状态流转和审核意见 | `record_id`、`action`、`from_status`、`to_status`、`comment`、`actor_id`、`diff`、`created_at` |
| `biz_record_version` | 不可变的发布快照 | `record_id`、`version_no`、`payload`、`schema_version`、`published_by`、`published_at` |

约束要点：

- 同一数据集同一业务主键只有一条未删除的 `biz_record`，由部分唯一索引保证。
- 状态：`draft` → `pending_dept` → `pending_domain` → `pending_center` → `published`，另有 `returned`、`archived`。规则以需求文档 3.3 节为准。
- 审核环节序列由数据域和 `filler_type` 共同计算：
  - 教师填写：系部初审 → 业务部门审核 → 信息中心审核；获奖信息没有业务部门审核环节。
  - 系部代填：从业务部门审核开始；获奖信息直接进入信息中心审核。
  - 业务部门审核员填写本部门数据域：直接进入信息中心审核。
  - 信息中心填写：可直接发布。
- 信息中心可在任一待审状态执行“跳级发布”，必须填写说明。
- 已发布记录再编辑时回到 `draft`，新版本发布前 `ODS_*` 中仍保留上一版本。
- 发布在一个事务内完成：重新校验 → 按业务主键写入 `ODS_*` → 写版本快照 → 写事件与审计。
- 电子表格导入、AI 候选确认、API 采集都只能生成草稿或提交进入审核，不能直接发布。

### 3.3 数据集注册表

在 `backend/app/datasets/` 下为每张表声明一个规格对象：

- 基本信息：编码、名称、对应 `ODS_*` 模型、业务主键字段、范围字段（如教工号字段、院系部字段）。
- 权限：数据域类别（教师类 / 教务类）、业务审核部门。业务审核部门取部门编码（`BM11` 组织人事部、`BM22` 科研处、`BM07` 教务处），或取 `owner_department` 表示由记录所属系部审核（获奖信息）。填写与审核权限按需求文档 3.4 节由这两项推导，不在每张表重复配置。
- 字段列表：编码、名称、类型、长度、是否必填、字典编码、条件显示与条件必填、分组、是否敏感。
- 校验钩子：表达不了的规则用函数补充，例如教职工的身份证一致性、职称四项同填。

由此提供通用接口：

| 方法与路径 | 说明 |
| --- | --- |
| `GET /api/datasets` | 当前用户可见的数据集目录 |
| `GET /api/datasets/{code}/meta` | 字段元数据、字典取值、可选部门 |
| `GET/POST /api/datasets/{code}/records` | 列表（分页、筛选）与新建草稿 |
| `GET/PUT/DELETE /api/records/{id}` | 查看、编辑草稿、删除草稿 |
| `POST /api/records/{id}/submit`、`/withdraw` | 提交与撤回 |
| `POST /api/records/{id}/review` | 当前环节通过或退回（退回须填意见）；信息中心环节通过即发布 |
| `POST /api/records/{id}/publish` | 信息中心跳级发布（须填说明） |
| `GET /api/reviews/todo` | 当前用户各审核环节的待办 |
| `GET /api/datasets/{code}/template`、`POST /api/datasets/{code}/imports` | 下载电子表格模板、上传导入 |
| `GET /api/records/{id}/events`、`/versions` | 流转记录与历史版本 |

现有 `/api/staff` 接口在教职工迁移到通用接口后下线。

## 4. 决策记录

### 4.1 已确认（2026-11-04）

| 事项 | 决定 | 对开发的影响 |
| --- | --- | --- |
| `ODS_*` 用途 | 草稿和审核中的数据放在填报记录表，`ODS_*` 只存已发布数据 | 按第 3 节实现填报记录层 |
| 审批流程 | 系部初审 → 业务部门审核 → 信息中心审核发布；信息中心可跳级发布 | 三级状态机与跳级发布，详见需求文档 3.3 节 |

| 业务部门审核员 | 组织人事部、科研处、教务处各设审核员，既能审核也能填写本部门数据域 | 已建测试账号；审核员本人填写的记录直接进入信息中心审核 |
| 发送 DeepSeek 的内容 | 不剔除身份证号等字段 | `AI_REDACT_FIELDS` 默认为空 |
| 身份证号 | 明文保存 | 不做加密；保留界面脱敏和明文查看授权 |
| 九月新生数据 | 后续再处理 | `ODS_XSXSSJ` 不进入首版注册表 |
| 业务系统接口 | 最后对接，先用电子表格 | 电子表格导入提前到 M4，API 采集移到最后 |
| DeepSeek | 已获审批 | M5 可直接接入 |
| 部门编码 | 公共基础教学部为 `BM09` | 数据库和种子均已是 `BM09`，无需改动 |

## 9. 环境初始化与运行

### 9.1 前置软件

- Python 3.12+，uv
- Node.js 22+ 与 npm（使用项目 `.npmrc` 中的 npmmirror 镜像）
- PostgreSQL 15+。当前开发机为 Postgres.app 15.19，库名 `qxnzy_das`，用户和密码均为 `postgres`
- Redis 仅 worker 需要；Docker 为可选项，只在没有本机数据库时使用（`docker compose up -d postgres`）

### 9.2 后端

```bash
cd backend
cp .env.example .env
uv sync
uv run alembic upgrade head
uv run python -m app.seeds.initial_data
uv run fastapi dev app/main.py
# 任务模块完成后另开终端启动 worker
uv run arq app.workers.settings.WorkerSettings
```

需在 `backend/` 目录下启动，配置只读取当前目录的 `.env`。API 地址 `http://localhost:8000`，文档 `http://localhost:8000/docs`。

### 9.3 前端

```bash
cd frontend
cp .env.example .env.local
npm install
npm run dev
```

前端地址 `http://localhost:3000`。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 业务部门审核员未落实到人 | 三级审批卡在业务部门环节 | 测试账号已建；上线前落实正式名单；信息中心可跳级发布兜底 |
| 审核员拥有全校填写权限 | M2 完成前可能越过数据域填写 | 教职工接口已按部门临时限定；M2 由注册表统一判断，新增数据集接口一律走注册表权限 |
| 电子表格格式不统一 | 教务处导入失败率高 | 只接受系统生成的模板；逐行错误报告；M4 前收集真实样例 |
| 十二张表逐张手写 | 周期长、口径不一致 | 数据集注册表统一驱动，特殊规则才写钩子 |
| AI 提取不稳定或提示词注入 | 错误数据、泄露风险 | 文件内容视为不可信输入；结构化输出、人工确认、黄金集评估 |
| 敏感材料发送校外模型 | 合规风险 | 已获数据出校审批；日志不记录正文；保留 `AI_REDACT_FIELDS` 以便按字段剔除；政策变化时切换校内模型 |
| 来源 API 无增量或不稳定 | 漏采、重复 | 全量对账、来源主键幂等、水位线、重试和隔离区 |
| 多来源覆盖人工数据 | 数据回退 | 字段级权威来源与冲突策略，保留版本与修改历史 |
| 行级权限遗漏 | 个人信息泄露 | 统一查询依赖、默认拒绝、越权自动化测试和审计 |
| 长期不提交代码 | 改动丢失、无法回溯 | 每个任务完成即提交，M1 收尾先提交现有改动 |

## 11. 完成定义

每个数据域只有同时满足以下条件才算完成：

1. 字段、字典、唯一规则和责任部门已经确认，并在数据集注册表中声明。
2. 表单、权限、校验、审核、发布、历史版本和共享接口均已实现。
3. 适用的 AI 文件解析与来源 API 链路通过真实样例联调。
4. 迁移、错误处理、审计、敏感字段处理和 OpenAPI 已更新。
5. 正常、边界、越权、重复、失败重试和回退场景有自动化测试。
6. 业务部门使用脱敏或试运行数据完成验收，无 P0 缺陷。
