## 1. 实施策略

采用“标准先行、纵向打通、逐域复制”的方式：

1. 先确认字段、权限和审核规则，避免十二张表分别形成不同口径。
2. 用“教师获奖信息”打通表单、AI 文件填报、审核发布和共享 API 的完整链路。
3. 用“课程基本数据”打通 API 采集、幂等更新和增量共享链路。
4. 将验证后的公共能力推广至其余数据域，再完成历史数据、试运行和上线。

AI 只负责生成候选数据，业务确认和审核是独立步骤；异步任务不直接写已发布表。

## 2. 技术架构

```text
浏览器（Next.js App Router）
  ├─ 服务端组件：页面框架、目录与首屏授权数据
  ├─ 客户端组件：表单、表格、上传进度与候选确认
  └─ HTTPS / JSON
             ↓
FastAPI（认证、RBAC、业务、审核、共享 API）
  ├─ SQLAlchemy 2.0 → PostgreSQL
  ├─ arq 入队 → Redis → arq worker
  │                    ├─ pandas/openpyxl/pdfplumber/python-docx
  │                    ├─ DeepSeek / 校内 OpenAI 兼容模型
  │                    └─ 来源系统 API 拉取
  └─ 受控文件存储（首版本地/共享卷，可换对象存储）
```

关键设计：

- PostgreSQL 是业务状态唯一权威来源；Redis 只承担队列和短期协调，不作为业务结果存储。
- 文件任务和采集批次状态落库，worker 崩溃后可识别并重试。
- 所有写操作使用事务；来源唯一键、业务唯一键和任务幂等键由数据库约束兜底。
- AI 适配层接受模型提供方、URL、密钥和模型名配置，通过结构化输出和 Pydantic 双重约束。
- 共享 API 与管理 API 分开认证和授权，均输出结构版本与数据版本。
- 大文件分片解析、模型分批调用，限制单批记录数和上下文长度。

## 7. 环境初始化与运行

### 7.1 前置软件

- Python 3.12+
- Node.js 22+ 与 npm
- uv（推荐，用于 Python 依赖与虚拟环境）
- PostgreSQL 15+。当前开发机为 Postgres.app 15.19，库名 `qxnzy_das`，用户和密码均为 `postgres`
- Docker 及 Docker Compose 为可选项，只在没有本机数据库时使用

### 7.2 启动本地依赖

本机已有 PostgreSQL 时直接使用，不要停掉占用 `5432` 的进程。没有本机数据库时再启动容器：

```bash
docker compose up -d postgres
```

Redis 只给尚未接入任务的 worker 使用。启动 API 不需要 Redis。

### 7.3 后端

```bash
cd backend
cp .env.example .env
uv sync
uv run alembic upgrade head
uv run python -m app.seeds.initial_data
uv run fastapi dev app/main.py
# 另一个终端启动异步 worker（任务模块完成后使用）
uv run arq app.workers.settings.WorkerSettings
```

API 默认地址为 `http://localhost:8000`，文档为 `http://localhost:8000/docs`。

### 7.4 前端

```bash
cd frontend
cp .env.example .env.local
npm install
npm run dev
```

前端默认地址为 `http://localhost:3000`。npm 使用项目 `.npmrc` 中的 npmmirror 镜像。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 字段和部门职责迟迟未确认 | 重复开发、口径冲突 | 第 1 周冻结 V1；变更走评审和结构版本 |
| AI 提取不稳定或提示词注入 | 错误数据、泄露风险 | 文件内容视为不可信输入；结构化输出、人工确认、权限隔离、黄金集评估 |
| 敏感材料发送校外模型 | 合规风险 | 数据出校审批、脱敏、字段白名单；不满足条件时先使用校内模型 |
| 文件过大或模型超时 | worker 堆积 | 文件/页数/行数限制、分批、超时、有限重试、并发上限和死信处理 |
| 来源 API 无增量或不稳定 | 数据漏采、重复 | 全量对账、来源主键幂等、水位线、重试和隔离区 |
| 多来源覆盖人工数据 | 数据回退 | 字段级权威来源和冲突策略，保留版本与修改历史 |
| 行级权限遗漏 | 个人信息泄露 | 统一查询依赖、默认拒绝、越权自动化测试和审计 |
| 十二类数据同时开发 | 周期长、问题晚暴露 | 两个纵切片先验收，再复用公共能力扩展 |
| 本地文件存储单点 | 文件丢失、扩容困难 | 独立卷、备份、存储抽象，后续迁移对象存储 |

## 9. 完成定义（Definition of Done）

每个数据域只有同时满足以下条件才算完成：

1. 字段、字典、唯一规则和责任部门已经确认。
2. 表单、权限、校验、审核、发布、历史和共享 API 均已实现。
3. 适用的 AI 文件解析与来源 API 链路通过真实样例联调。
4. 数据库迁移、错误处理、审计、敏感字段处理和 OpenAPI 已更新。
5. 正常、边界、越权、重复、失败重试和回退场景通过测试。
6. 业务部门使用脱敏或试运行数据完成验收，无 P0 缺陷。

## 10. 上线检查

- 生产密钥由安全渠道注入，DeepSeek 密钥不进入代码库和前端环境变量。
- CORS、应用凭证、调试文档、日志脱敏和文件限制符合生产要求。
- PostgreSQL、Redis、文件目录持久化并完成备份恢复演练。
- worker 与 Web 服务分别配置并发、超时、健康检查和重启策略。
- 完成历史数据核对、下游抽样对账、用户培训、回滚方案和值班安排。
- 自部署模型切换前使用同一黄金数据集对比，经灰度和业务确认后启用。
